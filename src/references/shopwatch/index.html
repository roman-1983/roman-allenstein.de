The problem

Shop operators usually learn about a problem from the sales figures. The checkout got half a second slower, a trust badge stopped rendering, a deployment dropped the canonical tags - none of that raises an alarm, and by the time the revenue dip is visible in a report, the cause is weeks old and buried under everything else that changed since.

The tooling for each individual question exists, and that is exactly the problem: performance in one tool, SEO in the next, certificates and trust signals somewhere else again, each speaking its own dialect and each assuming a specialist is reading it. The person actually responsible for the shop is rarely that specialist. ShopWatch answers one question instead - is my shop healthy, and if not, what do I fix first?

What it does

  • One composite score Sixty-plus individual checks across eight families - performance, SEO, advanced SEO, markup, trust, best practices, tech stack, social - roll up into a single ShopWatch Score with a breakdown per category.
  • Tracked over time Every run is a measurement, not a snapshot, so a regression shows up as a curve bending rather than a number someone has to remember.
  • Uptime and incidents Reachability is checked continuously; outages are classified into incidents instead of firing one alert per failed probe.
  • Findings with a next action Results are not a list of red items. Findings carry progress state and are ranked into a next-best-action, so there is always one obvious thing to do next.
  • Competitors The same checks run against competing shops, so a score can be read against the market instead of in a vacuum.
  • Workspaces and agencies Accounts, workspaces, members and invitations, so an agency can run many client shops side by side under its own roles.
  • Passwordless access Sign-in runs on one-time codes by email - no password to leak, and one less obstacle between a visitor and their first result.
  • Plans and billing Subscriptions, entitlements, invoices and proration on plan changes, with limits enforced through a single entitlement service.

How it is built

Symfony on PHP 8.4, PostgreSQL with TimescaleDB hypertables for the measurement series, everything containerised. Checks are small classes behind a registry - some parse fetched HTML, others call external services - which is what makes sixty of them maintainable: adding a check means writing one class, not touching a pipeline.

The work happens outside the request, on nine named queues - registration, page speed, analysis, communication, payment and prioritised general lanes - consumed by around a dozen worker containers with their own retry strategies. That separation is the point: a slow third-party API on one shop's page-speed run must never delay somebody else's sign-up, and a payment webhook must never queue behind a batch of analyses.

Around the edges sit the parts that make it a product rather than a script: a scheduler for recurring runs, alert evaluation against thresholds, bot-wall detection so a shop that blocks crawlers is reported as blocked instead of broken, and vector embeddings of shop profiles to suggest which competitors are worth comparing against.

The interesting part

The hardest problem is not measuring anything - it is the score. A number that aggregates sixty checks is only useful if people trust it, and trust breaks the moment it moves for a reason nobody can explain. So every score decomposes into categories, every category into checks, and every check into the evidence it was derived from. A score you can argue with is worth more than a score that is merely precise.

The second lesson came from the open internet. Shops rate-limit, serve different markup to bots, sit behind protection that answers with a challenge page, or are simply slow. Treating those as failures produces alarms nobody believes, so a good share of the code is about telling could not measure apart from measured and it is bad - and saying so plainly.
